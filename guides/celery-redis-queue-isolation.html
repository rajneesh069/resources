Celery · Redis broker

When two Celery workers share a Redis queue

One Redis instance is a train of 16 compartments (logical DBs, /0–/15). Each compartment holds named shelves (Celery queues). A worker binds to exactly one (compartment, shelf) pair — and a task is only stolen when two workers share both. If nobody sets a queue, every worker defaults to the shelf named celery.

Every instance owns a distinct (compartment, shelf). The default celery shelf still exists in Service A's DBs — just empty and unwatched.

Two independent locks

Either one alone stops the theft. Use both — they're cheap, and they cover different failure modes.

Lock 1 — Compartment (Redis DB)

Point the worker at a different logical DB (REDIS_URL …/1 → …/10). Different compartment → the queues can't overlap even if both are named celery. Also isolates the control channel & memory keyspace.

Lock 2 — Shelf (Celery queue)

Give each app its own queue: task_default_queue = "<app>_<env>_bg". Backs up Lock 1 against a mis-set DB — and it's the only thing keeping two instances of the same service from silently running each other's tasks if they ever share a compartment.

The trap: multiple apps on one Redis instance all defaulting to DB /0 + queue celery.
The fix pattern: unique task_default_queue per app, and a dedicated Redis DB per app/environment.
